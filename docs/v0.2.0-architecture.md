# v0.2.0 架构说明

## 核心选择

“甲方组织库”和“人脉库”是两套独立的业务主数据，不是两个物理数据库。v0.2.0 使用一个独立 PostgreSQL 数据库，以便外键、事务、审计和备份保持一致；组织与联系人分别建表，再通过任职关系建立多对多连接。

```text
organizations ──< contact_affiliations >── contacts
      │                                      │
      └──< business_item_organizations       │
                         business_items >────┘
                         business_item_contacts
```

主要表：

- `organizations`：公司、子公司、机构等组织主体。
- `organization_units`：组织内部部门、分支、团队层级。
- `contacts`：与任职单位解耦的自然人档案。
- `contact_affiliations`：联系人在组织中的任职、角色、主关系、有效期、来源和置信度。
- `business_items`：拜访与待办的共同事项基表。
- `business_item_organizations`、`business_item_contacts`：事项与两套主数据的独立多对多关系。
- `attachments`：事项附件元数据；文件内容进入对象存储。
- `audit_logs`：登录和关键写操作的审计事件。

## 历史一致性

事项创建时会把组织、联系人及其当时任职信息写入 `relation_snapshot`，同时在两张事项关系表保存单项快照。联系人调职、组织改名或主数据停用后：

- 当前主数据界面显示最新信息；
- 历史事项仍可还原发生当时的组织和任职语境；
- 任何修改均写入审计日志。

## 权限边界

- `admin`：系统配置、主数据和事项全权限。
- `manager`：部门主数据、事项和审计查看权限。
- `member`：创建和维护主数据、拜访与待办。
- `readonly`：仅查看。
- 私有人脉仅本人、经理和管理员可见。
- 自助注册只能进入配置的默认部门，角色固定为 `member`，不能通过注册接口提升权限。
- 只有 `admin` 可以新增、启停账号、调整角色或重置他人密码。
- 每个部门必须保留至少一个启用的管理员；当前账号不能自行降级或停用。
- 密码、角色和账号状态变化会递增 `auth_version` 并撤销刷新令牌，使所有旧会话立即失效。

## 账号入口

- 登录：用户名 + 密码，失败请求受频率限制。
- 注册：用户名 + 姓名 + 密码；内网由 `SELF_REGISTRATION_ENABLED` 显式开启。
- 密码策略：12–128 位，同时包含大小写字母、数字和特殊字符。
- 账号安全操作只记录动作、操作者和目标账号，不写入明文密码或密码哈希。

## 部署边界

Compose 项目固定为 `business-management`，拥有自己的镜像、容器、网络、数据目录和备份目录：

```text
Web :8088 ── edge ── API ── data(internal) ── PostgreSQL
                              ├────────────── MinIO
                              ├────────────── DB backup
                              └────────────── Attachment backup
```

数据库和对象存储均不发布宿主机端口。考虑到当前 MinIO 单节点启动时会预分配约 1 GiB，默认运行时内存上限总和约 2.2 GiB；各服务仍保持独立限额，并与服务器现有现场检测业务隔离。
