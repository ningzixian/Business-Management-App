# 系统检查与组织层级改造报告

检查日期：2026-09-08。对象：当前工作区代码、浏览器本地演示环境、内网服务健康状态，以及隔离事务中的 PostgreSQL 迁移。

## 结论与边界

本轮发现多项会影响真实使用的问题，不能认定系统已通过完整验收。下表明确区分真实点击复现、代码审查和待专项验证；编译或单元测试通过不等于功能端到端通过。

本次只实施用户明确要求的名称与组织层级改造，以及层级选择所需的完整分页加载。其余问题列出，未批量改动业务逻辑。

- 本地源码已修改，未提交 Git，未部署正式 Web/API，未发布新 APK。服务器仍是原版本。
- 本地浏览器在演示模式测试，新增了“测试商务部”“测试待办说明保留”，仅存于该测试浏览器的本地演示数据，不是正式数据。
- 数据库测试创建独立随机 schema，依次执行 001、002、003 迁移和断言，最终 `ROLLBACK`。未迁移正式 schema，未写入正式组织表。
- 只读检查确认商务 Web/API/数据库/附件存储健康，检测前后端健康；未修改检测容器、数据库、配置或备份。

## 本次完成的改造

1. Web 与手机界面中的“甲方组织库”改为“组织”，“人脉库”改为“人脉”。
2. 新增组织可选择类型（新增“部门”）及上级组织；部门可以归属公司，也可以归属另一部门。
3. Web、手机组织页均有可展开的组织架构树，可调整现有组织的上级，也可清空上级成为一级组织。
4. 调整组织时，下级随之移动；组织 ID 不变，已有的人脉任职、事项关联不变。只读账号不显示调整上级按钮。
5. 上级选项、任职组织选项、事项组织选项展示完整路径，区分不同公司下的同名部门。
6. 接口返回上级 ID/名称，创建/修改保存父节点关系。防止自己作为上级、下级作为上级，并在部门数据域内串行化层级写入，避免并发成环；有下级时拒绝删除父节点。
7. 003 迁移增加部门类型、禁止自身父节点、父子同数据域外键约束；同一上级下名称唯一，不同上级可以有同名部门。
8. 组织、人脉、事项原先仅加载前 100 条，现按 API 页数加载完整列表，避免层级选项截断。超大数据量仍需后续服务器筛选和按需树加载。

采用一个业务数据库中的独立 organizations / contacts 表，人脉不混入组织树；通过 contact_affiliations 多对多关联。组织层级只保存 parent_organization_id，层数和路径动态推导，避免移动组织时冗余层级字段失真。旧 organization_units 表和记录保留，不自动转换；新增公司/部门统一走 organizations 树。如旧 units 已有实际任职数据，正式迁移前需核对是否需要合并。

## 复测与发布

本地代码检查：`npm run verify`。数据库隔离测试：`deployment/test-hierarchy-migration.ps1 -Credential <PSCredential>`；脚本只指向商务数据库容器，临时 schema 和测试数据随事务回滚。

正式发布前先备份商务数据库并核对存量层级，部署 API 执行 003 迁移，再发布匹配的 Web。手机共用源码也需重新构建并提升 Android versionCode 后发布新 APK，旧 APK 不会因为 Web 发布自动获得此次前端改动。

建议修复顺序：权限与输入丢失 → 真实日期/统计/周报 → 拜访编辑与转待办 → 任职/附件闭环 → 手机按钮/通知/弹窗 → 真机与恢复验收。不要直接把当前状态认定为已具备完整正式业务闭环。
